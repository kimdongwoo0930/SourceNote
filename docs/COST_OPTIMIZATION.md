# 캐싱 & 비용 최적화


## BYOK를 채택한 이유

이 프로젝트에서 발생하는 API 비용은 성격이 둘로 명확히 갈립니다.

| | 임베딩 | 질문답변 · 문제생성 |
|---|---|---|
| 발생 시점 | 문서를 넣을 때 **한 번** | 사용자가 쓸 때마다 |
| 누적 방식 | 자료 양에 비례 (유한) | `사용자 수 × 호출 수` (무한) |
| 단가 | 100페이지 ≈ **2원** | 1회 ≈ **0.8원 ~ 13원** |
| 부담 주체 | **개발자 고정 키** | **사용자 본인 API 키** |

임베딩은 자릿수가 다르게 저렴하고 한 번만 발생하므로 개발자가 흡수해도 됩니다. 반면 추론 비용은 사용자가 많아지고 오래 쓸수록 무한히 누적되고, 고가 모델을 고르면 질문 하나에 13원입니다. 1인 개인 프로젝트가 감당할 항목이 아닙니다.

그래서 **추론만 사용자 본인 키(Claude 또는 GPT 중 선택)로 분리**했습니다.

**이게 대중 서비스에 적합한 선택이 아니라는 건 알고 있습니다.** 일반 사용자에게 "API 키를 발급해서 붙여넣으세요"를 요구하는 건 가입 전환율을 죽이는 요구사항입니다. 하지만 이 프로젝트의 목표는 사용자 확보가 아니라 **멀티유저 환경에서 인증·권한·비용을 사용자 단위로 분리한 시스템을 끝까지 완성해 보는 것**입니다. 그 기준에서는 BYOK가 오히려 설계 난이도를 올려 줍니다.

BYOK 때문에 실제로 풀어야 했던 문제들:

- 사용자별 API 키를 **암호화 저장**하고 응답에서 마스킹 (`Settings.llm_api_key`)
- provider·key·model이 요청마다 다르므로 **ChatModel을 고정 빈으로 둘 수 없음** → 요청 시점 생성 → [ARCHITECTURE.md](ARCHITECTURE.md#chatmodel을-고정-빈으로-두지-않는-이유)
- 키 유효성 검증과 모델 목록 조회를 **사용자 키로 제공사 `/v1/models`를 호출**해 처리 (Anthropic/OpenAI 인증 헤더가 서로 다름)
- 임베딩(서버 키)과 추론(사용자 키)의 **비용을 한 테이블에서 분리 집계** (`LlmUsageLog.operation_type`)

## 캐싱 전략

| 종류 | 목적 | 구현 |
|---|---|---|
| **동일 질문 캐싱** | 완전히 같은 질문의 재호출 차단 | Redis (질문 해시 → 답변) |
| **시맨틱 캐싱** | 의미가 비슷한 질문도 캐시 히트 — **절감 임팩트 최대** | 질문 임베딩 유사도로 과거 질문 매칭 |
| **프롬프트 캐싱** | 반복되는 시스템 프롬프트·chunk의 입력 토큰 절감 | 제공사 prompt caching 기능 |
| **임베딩 중복 방지** | 같은 chunk 재임베딩 차단 | 텍스트 해시 비교 후 스킵 |
| **배치 임베딩** | 대량 업로드 비용 절감 | Batch API (실시간 대비 50% 할인) |

### 왜 시맨틱 캐싱이 가장 중요한가

해시 기반 동일 질문 캐싱은 **글자 하나만 달라도 빗나갑니다.** "TCP 3-way handshake 설명해줘"와 "TCP 쓰리웨이 핸드셰이크가 뭐야"는 같은 답을 원하지만 해시가 다릅니다. 학습용 질문은 이런 재표현이 특히 많습니다.

시맨틱 캐싱은 질문을 임베딩해 과거 질문 벡터와 비교하고, 유사도가 임계치를 넘으면 저장된 답변을 재사용합니다. **추가 비용은 질문 임베딩 1회(≈0.0000x원)이고 아끼는 건 LLM 호출 1회(0.8~13원)** 라서 비용 구조상 거의 항상 이득입니다.

> **미정**: 과거 질문 임베딩을 어디에 둘지 확정되지 않았습니다. Qdrant에 별도 컬렉션(`question_cache`)을 두거나 Redis에 벡터를 직접 저장하는 두 안이 있고, 구현 시 결정해 [decisions/](decisions/)에 기록합니다.

### 임베딩 중복 방지

Notion 재동기화는 페이지 전체를 다시 가져옵니다. 문단 하나만 고쳐도 전체를 다시 임베딩하면 낭비이므로, chunk 텍스트 해시를 비교해 **변하지 않은 chunk는 임베딩을 건너뜁니다.** 페이지 단위 `last_edited_time` 비교(→ [ARCHITECTURE.md](ARCHITECTURE.md#notion-재동기화))와 chunk 단위 해시 비교가 2단 필터로 동작합니다.

## 비용 추적 (`LlmUsageLog`)

외부 API를 호출하는 모든 경로는 로그를 남깁니다. **캐시 히트도 기록합니다** — 그게 절감액을 계산하는 근거입니다.

```
LlmUsageLog (user_id, subject_id, operation_type, model_name,
             input_tokens, output_tokens, estimated_cost,
             cache_hit, cache_type, created_at)
```

| 컬럼 | 쓰임 |
|---|---|
| `operation_type` | 임베딩 / 질문답변 / 문제생성 / Notion동기화 — 기능별 분해 |
| `subject_id` | 과목별 비용 (어느 과목이 돈을 쓰는지) |
| `model_name` | 저가·고가 모델 비교 |
| `cache_hit`·`cache_type` | 캐싱 적용 전후 절감액을 수치로 산출 |

`cache_hit = true`인 행은 **실제로 지불하지 않았지만 지불했을 금액**을 `estimated_cost`에 기록합니다. 그래서 `SUM(estimated_cost) WHERE cache_hit = true`가 곧 캐싱이 절약한 금액이 됩니다.

### 사용량 대시보드

`LlmUsageLog` 집계 쿼리만으로 다음을 산출합니다.

- 기간별 총 사용액
- 기능별 분해 (임베딩 / 질문답변-저가 / 질문답변-고가 / 문제생성 / Notion동기화)
- 일별 추이
- 과목별 비용·호출 수

API → [API.md](API.md#usage-사용량)

## 비용 계산 근거

### 임베딩 — `text-embedding-3-small`, $0.02 / 1M 토큰

```
전공서 100페이지 ≈ 70,000 토큰
70,000 / 1,000,000 × $0.02 = $0.0014  ≈  2원
```

100페이지 PDF 한 권을 통째로 인덱싱해도 **2원**입니다. 개발자 부담으로 잡은 근거입니다.

### 질문 1회

입력 토큰은 대부분 근거 chunk입니다. top-5 × ~400토큰 ≈ 2,000토큰에 시스템 프롬프트와 질문을 더해 **약 2,200 입력 토큰 / 350 출력 토큰**으로 잡았습니다.

| 모델 등급 | 질문 1회 | 100회 |
|---|---|---|
| 저가 모델 | **약 0.8원** | 약 80원 |
| 고가 모델 | **약 13원** | 약 1,300원 |

같은 질문이 저가/고가 사이에서 **16배** 차이 납니다. 그래서 설정 화면에서 사용자가 모델을 직접 고르게 하고, 사용량 대시보드에서 저가·고가를 분리해 보여줍니다.

### 정리

```
임베딩 100페이지   ≈  2원      (한 번, 개발자)
질문 100회 (저가)  ≈  80원     (반복, 사용자)
질문 100회 (고가)  ≈  1,300원  (반복, 사용자)
```

문서를 넣는 비용은 사실상 무시할 수 있고, **쓰는 비용이 전부**입니다. 캐싱을 질문 경로에 집중시킨 이유이자 BYOK 경계를 여기서 그은 이유입니다.
