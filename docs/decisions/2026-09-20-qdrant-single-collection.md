# Qdrant를 단일 컬렉션으로 운영

- **날짜**: 2026-09-20
- **상태**: 확정
- **관련**: [DATABASE.md](../DATABASE.md#qdrant)

## 배경

멀티유저 서비스에서 벡터를 어떻게 격리할지 정해야 한다. 사용자가 남의 자료를 검색하는 일은 절대 없어야 한다.

## 선택지

1. 사용자별 컬렉션
2. 과목별 컬렉션 (`user_id`+`subject_id` 조합)
3. **단일 컬렉션 `study_chunks` + payload 필터**

## 결정

3번. 컬렉션 하나에 전부 저장하고 `user_id`·`subject_id` payload 필터로 범위를 좁힌다.

## 근거

- 2번은 컬렉션 수가 `사용자 × 과목`으로 늘어난다. Qdrant는 컬렉션마다 별도 HNSW 인덱스·세그먼트를 유지하므로, 벡터 총량은 같은데 인덱스 오버헤드와 메모리만 증가한다. 릴리즈 서버가 2 OCPU·12GB라 여유가 없다.
- 요구사항에 **"전체 자료 검색"** 옵션이 있다. 단일 컬렉션이면 `subject_id` 필터를 빼면 끝이지만, 컬렉션을 나누면 N개에 병렬 질의하고 점수를 직접 병합·재정렬해야 한다.
- 컬렉션을 나누면 과목 생성·삭제마다 컬렉션 생성·삭제가 붙는다. MySQL 트랜잭션과 원자적으로 묶이지 않아 중간 실패 시 정합성이 깨진다. 단일 컬렉션에서는 과목 삭제가 필터 삭제 한 번이다.
- payload 인덱스를 걸면 HNSW 필터 검색으로 충분하다. 개인 학습 자료 규모(사용자당 chunk 수만 개)에서 컬렉션 분리의 성능 이득은 사실상 없다.

## 트레이드오프

물리적 격리가 아니라 **필터에 의한 논리적 격리**다. `user_id` 필터를 빠뜨린 질의 하나가 곧 다른 사용자 데이터 노출이다.

완화: 벡터 검색 호출을 리포지토리 레이어 한 곳으로 모으고 거기서 `user_id` 필터를 강제 주입한다. 컨트롤러·서비스는 필터를 직접 조립하지 않는다.

## 영향

- payload 스키마: `user_id`, `subject_id`, `document_id`, `page_number`, `chunk_index`, `ingested_at`
- `user_id`·`subject_id`에 payload 인덱스 필요
- 삭제는 MySQL/Qdrant 양쪽에 걸치므로 **Qdrant를 먼저** 삭제한다 (고아 point가 남는 것보다 벡터 없는 문서 행이 안전)
